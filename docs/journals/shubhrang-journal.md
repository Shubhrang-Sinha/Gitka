Sprint 1 (Week 1: Oct 15 – Oct 21, 2026) — Core Foundation & Container Setup

Sprint Goal: Set up a local Docker environment that anyone can recreate (PostgreSQL + pgvector, Forgejo), and start the Next.js backend with the basic login system and health-check endpoints.

Oct 15 (Thu) — Sprint 1 Planning & Architecture Kickoff: Agreed with Saurya, Medha, and Akshita on a three-part self-hosted design: Next.js App Router (run with Bun), PostgreSQL 16 with pgvector for both regular table data and vector (meaning-search) data, and Forgejo for hosting Git repositories. Defined the Sprint 1 user stories (small tasks) and agreed on rules for keeping environments separate so secrets never get committed to Git.
Oct 16 (Fri) — Docker Compose & Running the Services Together: Wrote docker-compose.yml, .env.example, and the root .gitignore. Set up the pgvector/pgvector:pg16 service on host port 5433 and the Forgejo service (codeberg.org/forgejo/forgejo:15) on port 3001 (HTTP) and 2222 (SSH), with named volumes so data is kept.
Oct 17–18 (Sat–Sun) — Next.js Backend & Connection Pool Setup: Created the web/ Next.js 16 project with Bun and TypeScript. Wrote web/lib/db.ts, which uses one shared pg Pool (max: 5) and a pool error listener, so unused database connections that drop do not crash the Node/Bun program. Built GET /api/health/db to check that PostgreSQL and pgvector are ready.
Oct 19–20 (Mon–Tue) — Password Hashing, Sessions & Login APIs: Built web/lib/password.ts (password hashing with bcryptjs at cost factor 12, plus a check for the 72-byte UTF-8 limit) and web/lib/session.ts (createSession, getCurrentUser, destroySession, which use HttpOnly session_id cookies, meaning cookies that JavaScript in the browser cannot read). Built /api/auth/register, /api/auth/login, /api/auth/logout, and /api/auth/me, using safe parameterized SQL queries (placeholders for values) on the tables from Akshita's 001 and 002 migrations.
Oct 21 (Wed) — Sprint 1 Review & Retro: Showed the team docker compose up -d working, database migrations running, and API routes that use cookie login. Retro note: Running both Forgejo and Postgres fully in containers meant setting up Saurya's and Medha's local environments took under 5 minutes.
Sprint 2 (Week 2: Oct 22 – Oct 28, 2026) — AI PR Review Engine & Diff Parsing

Sprint Goal: Build the diff parser that always gives the same result for the same input, the review pipeline using the Vercel AI SDK + OpenRouter, and the PR review endpoint, so Gitka can analyze Forgejo pull requests automatically.

Oct 22 (Thu) — Sprint 2 Planning & Diff Parser Design: Worked with Saurya on how Forgejo provides unified .diff data and with Akshita on the pr_reviews / review_comments tables (010_pr_reviews.sql). Decided that the AI reviewer must always check line numbers against the real changed sections (hunks) of the new file before saving or posting comments.
Oct 23–24 (Fri–Sat) — Diff Parser (web/lib/diff.ts): Built parseDiff(raw), which splits a diff covering many files into separate files, decodes file paths that git writes in quoted form (octal/unicode escapes), and skips binary files, lockfiles, and minified files. It also labels every added or unchanged (context) line with its exact line number as L<num>, along with a validLines set (the lines that can receive comments) for each file.
Oct 25–26 (Sun–Mon) — OpenRouter AI Reviewer (web/lib/review.ts): Connected @openrouter/ai-sdk-provider to the Vercel AI SDK (generateText). Protected against prompt injection (text inside the code that tries to give the AI new instructions) by wrapping diffs in <diff> tags and treating them as untrusted. Required the AI's answer to follow a strict JSON format, sorted findings by severity (critical > warning > info), limited comments to 10 per PR, and added a fakeReview() fallback that always returns the same canned result when OPENROUTER_API_KEY is not set.
Oct 27 (Tue) — Manual Review Endpoint & Command-Line Test Scripts: Built POST/GET /api/projects/[id]/pulls/[n]/review/route.ts with a membership check (non-members get 404, so outsiders cannot discover which projects exist). Wrote web/scripts/try-diff.ts and web/scripts/try-review.ts to test diff parsing and the OpenRouter JSON output without using the screens.
Oct 28 (Wed) — Sprint 2 Review & Retro: Went over Sprint 2 progress together with Akshita's PR pages and Saurya's Forgejo PR poster (the code that posts reviews to Forgejo). Retro note: Smaller AI models (LLMs) gave wrong line numbers early on. Checking the AI's findings against validLines from diff.ts removed all (100%) of the review comment calls that Forgejo rejected.
Sprint 3 (Week 3: Oct 29 – Nov 4, 2026) — Preventing Clashes & Signed Webhooks

Sprint Goal: Make the AI PR review process safe against race conditions (two things happening at once and clashing), and deliver automatic reviews through signed Forgejo webhooks (automatic messages from Forgejo that include proof of where they came from).

Oct 29 (Thu) — Sprint 3 Planning: Found two serious reliability problems in Sprint 2 testing: several review clicks or webhooks arriving at the same time for the same commit (SHA), and the risk of webhooks that are not verified. Worked with Medha to keep the use of the web/lib/db.ts pool small while her SSE chat stream opened its own dedicated connections.
Oct 30–31 (Fri–Sat) — Review Controller & Taking Over Stuck Attempts (web/lib/run-review.ts): Built startReview() and runReview() using Akshita's 011_review_attempts.sql (attempt_token + publish_started_at). Built a takeover step that happens all at once (ON CONFLICT (project_id, pr_number, head_sha) DO UPDATE), so a retry after a failure, or a job that has been stuck in pending for 10 minutes (stale), gets a new UUID attempt_token. Every stage inside runReview() calls authorize(), so a worker that has been replaced stops with a StaleAttemptError before it can touch Forgejo or overwrite newer findings.
Nov 1–2 (Sun–Mon) — Signed Forgejo Webhook Handler: Built POST /api/webhooks/forgejo/route.ts, which verifies the HMAC-SHA256 signature (proof that the message really came from Forgejo) using FORGEJO_WEBHOOK_SECRET, with a comparison that cannot leak timing information. Handled the pull_request events opened and synchronized, starting startReview / runReview in the background and quickly returning 202, so Forgejo doesn't time out.
Nov 3 (Tue) — Docker Networking & Automatic Re-Tests: Changed docker-compose.yml (FORGEJO__webhook__ALLOWED_HOST_LIST: private) so the Forgejo container is allowed to send webhooks to host.docker.internal:3000. Wrote web/scripts/test-diff-paths.ts, web/scripts/test-stale-takeover.ts, and web/scripts/try-webhook.ts.
Nov 4 (Wed) — Sprint 3 Review & Retro: Tested taking over stuck attempts and automatic reviews through webhooks from start to finish, at the same time as Medha's real-time SSE team chat launched. Retro note: Adding test-stale-takeover.ts found a hidden problem: publish_started_at was not checked before a takeover was allowed.
Sprint 4 (Week 4: Nov 5 – Nov 11, 2026) — Background Workers & Stronger Protection for Many Users

Sprint Goal: Support Saurya's Codebase Q&A background worker process, and make the backend APIs safer with rate limiting stored in PostgreSQL.

Nov 5 (Thu) — Sprint 4 Planning: Agreed with Saurya on running Codebase Q&A indexing in the background, outside the time limit of a normal web request, and with Akshita on what the rate-limit table needs (040_rate_limits.sql).
Nov 6–7 (Fri–Sat) — Running Index Jobs With Leases: Worked with Saurya on web/lib/qa-jobs.ts and web/scripts/qa-worker.ts, using the same approach as in PR reviews, where a job's lease can expire (stale-lease pattern). If an indexing worker crashes, the job recovers automatically and the project is never locked out of refreshing its Q&A index.
Nov 8–9 (Sun–Mon) — Shared PostgreSQL Rate Limiter (web/lib/rate-limit.ts): Designed a rate limiter in PostgreSQL that counts requests in fixed time windows and updates the count in one step (INSERT ... ON CONFLICT DO UPDATE), so limits stay accurate across both the Next.js server and the background processes, without needing Redis. Applied limits to login (10 per minute per email, 120 per minute overall), registration (30 per minute), chat (30 per minute per user), Q&A questions (10 per minute per user), and index refreshes (3 per minute per project), with the standard Retry-After headers.
Nov 10 (Tue) — Clear Errors in Webhooks & Backend: Checked the API route handlers (login, register, messages, review) to make sure they all return errors in the same { ok: false, error } format, check input lengths strictly, and save errors in pr_reviews.error without slowing or blocking the request.
Nov 11 (Wed) — Sprint 4 Review & Retro: Showed the whole team a demo of Codebase Q&A and the shared Earl Grey look. Retro note: Using PostgreSQL for both rate limits and job leases kept the number of production containers small (db + forgejo + web + qa-worker), which made deployment much simpler.
